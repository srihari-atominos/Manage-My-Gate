# NAHOM Universal AI Assistant — Centralized Feature Inventory

Audit source: `backend/src/routes/api.routes.js`, `backend/src/features/*`, `mobile/mobile-app/src/features/*`, `frontend/src/features/*`, and the Gemini tool registry at `backend/src/features/aiAssistant/aiAssistant.tools.js`.

Every assistant request enters through `POST /api/v1/ai-assistant/chat` (or its Server-Sent Events streaming equivalent `POST /api/v1/ai-assistant/chat/stream`), is authenticated by the application's JWT and tenant middleware (`authenticateToken`, `tenantContextMiddleware`), and is executed strictly through authorized backend services.

- **Read Operations:** Executed directly via authorized backend service methods with server-side RBAC checks and data scoping.
- **State-Changing Operations (Mutations):** Follow the mandatory **Two-Phase Execution Pattern**:
  1. The assistant prepares a digitally signed, HMAC-SHA256 protected pending action proposal (`createPendingActionProposal`) bound to the authenticated `userId`, `orgId`, and exact sanitized parameters.
  2. The proposal is returned with an interactive confirmation card in the chat UI.
  3. Execution is only triggered when the user explicitly confirms via the card button or natural confirmation phrase ("Confirm", "Yes, go ahead"). The confirmation handler (`confirm_pending_action`) revalidates RBAC, tenant isolation, parameter tampering, and single-use idempotency before calling the backend service.

## 2. Authorization & Tenant Isolation Invariants

1. **Never Trust LLM or Client Claims:** The AI assistant NEVER derives or trusts roles, permissions, tenant `orgId`, or user IDs from LLM output or user chat text. All authorization and tenant boundaries are enforced strictly on the server using `req.user` and `req.tenant` populated by verified JWT auth middleware.
2. **Deterministic Two-Phase Mutation:** Any action that creates, updates, or deletes database records is quarantined behind an HMAC-SHA256 proposal (`aiAssistantActionSchema`). The secret key is held only by the server. Tampering with parameters or replaying expired tokens is rejected deterministically.
3. **Compound & Multi-Intent Safety:** Compound requests (e.g. "Show my dues, check pool availability, and list notifications") are segmented and evaluated independently. A permission denial on one operation does not compromise or prevent the execution of authorized read operations.
4. **Chat and Voice Parity:** The live voice agent and text chat share the exact same tool definitions, conversational state machine, permission gates, and execution engine.
